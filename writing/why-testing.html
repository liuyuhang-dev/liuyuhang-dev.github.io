要测试干嘛？

2026 · 刘禹杭 · AI 辅助成文

这三个问题我都被人当面问过，而且问的人不是外行。 第一个来自一个策划，第二个来自一个很懂 AI 的技术负责人，第三个来自一个做发行的朋友。 我当时的回答都不够好。这篇文章是重新想过之后的版本。

质疑一：闸门谁都能做，决策权本来就在上游

原话大概是：

你说要有"人工确认闸门"。可这个闸门策划能做、程序也能做，为什么非得是测试？ 而且真正拍板的是上游——需求是策划提的，排期是制作人定的，测试不就是最后盖章吗？

这条有一半是对的，而且是很重要的那一半。

对的部分：闸门本来就该在上游

如果测试只能在版本末期说"这里有问题"，那这个流程已经失败了。 好的质量体系里，大部分闸门确实在上游：

  • 需求评审阶段就应该拦掉"不可判定"的需求；
  • 设计阶段就应该确认不变量（金币不能为负、重放不能双倍）；
  • 编码阶段就该有静态检查和自测。

我们在项目里做的也是这个：9 条跨模块规则前置到评审阶段，配置表在出包前做零设备的静态交叉。 如果这些前置起作用，最后那道闸门应该很轻松。

不对的部分：闸门的价值不是"点同意"

这是我当时没答好的地方。我后来想清楚了：

闸门的价值不在于谁点那个"同意"，而在于"什么叫同意"是谁定义的。

举个具体的例子。我们做过一个 AI 只提议、人确认才落库的机制。 表面上看，确认的人是项目经理，不是测试。但真正约束这件事的是三样东西：

  1. 判定标准：什么算"拆得对"（每条需求子句至少一条用例、期望必须能指回来源）
  2. 证据要求：每条"已完成"必须挂 Git 提交，不能只写一句"做完了"
  3. 状态词表：不允许出现"应该没问题"，只有 pass / fail / blocked / skipped

这三样东西如果由被判定的人自己定，那就是自证。策划可以确认"我做完了"，但如果"做完"的定义是他自己写的，这个确认没有信息量。

所以问题不是"谁能做这个闸门"，而是：

判定标准必须独立于被判定对象。而这个独立性，需要一个结构上不被交付压力收买的人来守。

还有一层：激励，不是能力

策划完全有能力做判定。程序也完全有能力做判定。他们只是没有余量，也没有动机。

  • 策划的 KPI 是"按时上线"，不是"证明这个需求做不成"；
  • 程序的 KPI 是"交付"，不是"证明自己写的有问题"；
  • 制作人的 KPI 是"版本发出去"。

而"证明它不对"这件事，天然和所有人的 KPI 相反。

我不是说测试比他们高尚。我是说这个角色的激励结构不一样：他的产出就是"问题清单"，问题越多他越有价值。这个反向激励是制度设计，不是道德优势。

结论：决策权确实在上游，这一点我认。但上游做决策需要可信的输入，而可信的输入需要一个敢说"不"、且说了不没有代价的人。

质疑二：你的资产已经全变成"被执行的思想"，那还需要你吗

这条最狠，因为它说的就是我正在干的事。

你把方法写成了脚本、门禁、模板、维度表。机器照着跑就行了。 那这些东西越完善，你不就越没用吗？

这条基本是对的。但结论反了。

先承认：有一类工作确实会消失

如果一个人的全部价值是"按清单执行检查"——跑回归、点按钮、填报告——那这个岗位应该被替代，而且正在被替代。这没什么好辩护的，重复劳动被自动化是好事。

我也不打算说"AI 取代不了人的判断"这种空话。很多判断确实可以被取代，尤其是那些有明确规则的判断。

但"被执行的思想"有个前提

脚本只能执行你已经想到的规则。它不会自己长出新的规则。

一个具体的例子。我们的测试维度表，一开始是 12 类。后来变成 17 类。多出来的五类是什么？

  • 性能与稳定性
  • 网络与弱网
  • 安全与反作弊
  • 兼容性与本地化
  • 文案与术语正确性

这五类没有一类是脚本自己冒出来的。每一类都是：线上出了事故 → 有人判断"这不是偶发，这是一整类问题" → 才写进表里。

而最后那一类（文案与术语）尤其说明问题：它不是靠技术发现的，是靠"某天看到兑换码页面写着'获得响应奖励'"这种细节发现的。

脚本是被扩充的对象，不是扩充者。

这也是我在那套方法里写死的一条：维度表要"每出一次事故就变强一次"。变强这个动作，必须有人做。

真正的答案：工作往上移，不是消失

我不觉得"我不会被替代"。我觉得是：

我的产出物越自动化，我的工作就越往上游移动。

具体来说：

阶段 我在干什么 会不会被替代
执行检查 点按钮、跑回归、填报告 正在被替代，且应该被替代
设计判定 定义什么算通过、期望从哪来、证据要什么 部分可辅助，主体仍需人
定义"什么值得判" 判断哪类问题会让这个产品亏钱 目前看不到替代路径

第三行才是真正的位置。而它恰好需要第一、二行做底子——没跑过足够多的检查，就不知道哪类问题会真的发生。

结论：如果我的全部价值是执行，那我确实该被淘汰。如果我的价值是"在没人想到的地方补上一类新判定"，那自动化越彻底，这个价值越突出——因为剩下的都是难的。

质疑三：很多游戏一堆 bug 照样赚钱，要测试干嘛

这条最难反驳，因为它在大多数情况下是对的。

你看那些畅销榜上的休闲游戏，卡顿、穿模、文案错字、活动领不了奖，人家照样赚钱。 你们测试天天卡发版，卡出什么来了？

先认：质量不是越高越好

给一个买量驱动的休闲游戏做 99.9% 的质量，是浪费钱。质量的边际收益是递减的，而且递减得很快。

一个不影响核心循环的小穿模，修它花三天，这三天本可以用来做一个新关卡。这时候"不修"是对的决策。

如果测试的立场是"所有 bug 都要修"，那测试就是成本中心，而且活该被砍预算。

但"允许带 bug 上线"和"不需要测试"是两件事

真正的问题不是"要不要 bug"，而是：

哪一类 bug 可以带，哪一类不能带？

这个判断不能靠感觉。按我的经验，有四类 bug 是直接吃钱的：

类型 后果 为什么用户不会告诉你
支付 / 发货 直接漏钱，或者用户付了没收到 用户不会反馈，直接退款 + 差评 + 走
登录 / 存档 进度丢失，用户直接流失 买量成本白花，而且你看不到"他为什么走"
审核 / 合规 整包被拒，一天不上线就是一天的买量预算 这不算 bug，算事故
崩溃 / 启动失败 影响买量 ROI 和商店评分 商店评分掉了，买量单价直接涨

而下面这些，通常可以带：

  • 极端机型上的轻微卡顿
  • 某个活动里少见的文案错字
  • 非核心路径上的穿模

这两张表的分界线，就是测试该守的地方。

更锋利的一点

说"有 bug 也赚钱"的人，说的通常是别人的游戏。

轮到自己项目上线前一天，发现支付回调重复发货——没有人会说这话。

而且还有一层：能带 bug 上线，前提是你知道哪些 bug 可以带。 这个"知道"，本身就是测试的产出。没有测试的团队不是"允许带 bug 上线"，是"不知道自己带了什么上线"。

这两件事在赚钱的时候看不出区别，在出事的时候区别巨大。

结论：测试的目标从来不是零 bug，是把有限的质量预算，花在会直接影响收入的那几类问题上。这个判断本身，就是最值钱的部分。

三个质疑，其实是同一个问题

把它们放在一起看：

  1. 闸门谁都能做 → 判断权该归谁
  2. 方法被自动化了 → 人还剩什么用
  3. 有 bug 也赚钱 → 质量值多少钱

三个问题的答案其实是同一句：

当"做"变得越来越便宜，"判断"就变得越来越贵。 而判断的价值，取决于它是否独立、是否有证据、是否敢说"这个不能发"。

前两个质疑说的是"你的活被别人干了"，第三个说的是"你的活不值钱"。

我的回答是：如果我的活只是执行，这些话都对；如果我的活是判断，这些话反而证明了它为什么重要。

最后

我不觉得测试这个岗位天然存在。很多团队确实不需要专职测试——如果他们的产品足够简单，或者他们愿意承担相应的风险。

但任何团队都需要有人回答一个问题：这次发出去，最坏会坏在哪？

愿意回答这个问题、并且答得出来的人，不管叫不叫测试，都有位置。
