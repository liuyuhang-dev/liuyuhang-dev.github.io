点两次按钮，测不出重复支付

2026 · 刘禹杭 · AI 辅助成文

这是测试里最容易被"看起来测过了"骗过去的一类缺陷。 更糟的是，那种测法不仅没用，还会给团队一个假的安心。

一、大家是这么测的

需求里写「同一笔订单不能重复扣款」。测试怎么做？

打开商城，点购买，快速点两次。看到只扣了一次钱，标记通过。

这个动作看起来完全合理。它甚至经常真的能发现问题——在那些没做按钮防抖的早期版本里。

但它测的不是重复支付。它测的是"按钮会不会被点两次"。

二、真实的重复支付长什么样

重复支付不是用户手快，是系统自己重试。真实的五种来源：

场景 机制
响应丢失导致重试 请求发出 → 服务端处理成功 → 响应在回程丢了 → 客户端超时 → 重发 → 服务端处理两次
渠道回调重复投递 支付渠道（微信/抖音）回调超时会重投，同一笔订单的回调被投递多次
本地队列重放 离线期间的待处理订单排队，恢复后重放，与之前的成功请求叠加
进程被杀后重启 未确认状态的订单在重启后被重新提交
用户重复提交 唯一一个黑盒真能撞到的，但它恰恰是最少见的

界面上往往完全正常。 重复发货表现为"道具多了"，还算看得见；而"扣了两次钱只发一次货"，客户端根本看不出来——要去查服务端账目。

三、为什么"点两次"是伪覆盖

三个原因，每一个都足以让它失效：

  1. 大多数客户端有按钮防抖或置灰，第二次点击压根没发出请求；
  2. 即使发出了，走的是两次独立下单，不是"同一笔订单重复入账"——这两种错误的修复方式完全不同；
  3. 它永远触发不了回调重投、响应丢失重试、队列重放这三种真实机制。

所以结论是：

这种用例会给团队"重复支付已覆盖"的虚假信心。这比不测更糟。

不测，你知道这里有风险；假测，你以为没有。

我们后来把这条写进了规则：用例如果以"连续点击 N 次"作为重复支付的验证手段，校验器直接报警，复核必须驳回。

四、那怎么测：三层，从最便宜的开始

层 做什么 能发现 依赖
L2 静态 幂等防护缺失扫描 缺幂等键、缺状态守卫、缺回调去重 源码，不用运行
L3 运行时 精确时序故障注入 + 不变量判定 防护写了但失效 真机 + 状态上报
服务端 回调重投、重复入账对账 服务端那一半 服务端数据

关键认识是：

重复支付的根因是"结构性缺失"——该有幂等的地方没写。 所以最有效的检测不是跑测试，而是静态地找出这些缺失。

这恰好是"代码作为上游"的合法用法：代码告诉你该测哪里，但不告诉你应该是什么。

静态扫什么：四类防护

先定位所有有不可逆副作用的入口（下单、发货、结算、存档、排行、领奖），然后逐个查：

防护 检查什么 缺了会怎样
幂等键 请求带唯一订单号/请求 id 吗？服务端有唯一约束吗？ 同一请求被处理两次
状态守卫 状态流转有前置校验吗（只有"待支付"才能转"已支付"） 已完成的订单被再次推进
回调去重 处理回调前先查"这笔处理过吗" 渠道重投导致重复发货
重放去重 队列重放时检查该操作已成功吗 离线队列与成功请求叠加

产出不是"用例"，是两份清单：防护缺失清单（带文件名+行号）和覆盖地图（每一条边的失败/重试路径、可注入点）。

每条都要能定位到行号供人抽查——因为 AI 读代码会声称"这里没有防护"而实际有，或者在别处有。产出必须标注"待验证"。

运行时怎么注入

普通网络模拟太粗（只有延迟/丢包/断连），需要按动作定位的故障：

  • drop_response：请求发出后、响应到达前切断下行 → 模拟响应丢失
  • kill_after_step：某一步之后杀进程 → 模拟重启重放
  • offline_during_step：制造待处理队列
  • replay_callback：重投回调（客户端注入不了，需要服务端或代理）

四种能测，一种测不了。测不了的那一条要写进报告，而不是假装覆盖了。

五、判定靠什么：不变量，不是界面

重复支付在界面上不可见，所以判定必须靠状态上报 + 不变量：

不变量
同一订单只存在一条记录（按 orderId 唯一）
同一订单只发货一次
扣款次数 == 1
道具/货币增量精确等于单次预期值
订单状态单调不回退
待处理队列最终清空
回调处理计数与业务动作计数一致

其中一条值得单独说：

「增量精确等于单次值」比「增量大于 0」强得多。 后者对重复支付完全无感——发了两次货，增量是 2 倍，仍然大于 0。

还有最后一条容易被忽略：回调收了两次、只发了一次货，业务上看起来"没多发货"，但账目已经错了。所以要对两个计数，而不是只看结果。

六、边界：哪些是真测不了的

做不到 原因
服务端回调重投的真机覆盖 客户端注入不了回调
服务端重复入账的确认 客户端看不到服务端账目
真实支付渠道端到端 没有沙箱自动支付路径
真并发竞态 真机只有单客户端，造不出并发
保证防护"绝对正确" 静态扫描只能发现缺失，发现不了写错了

最后一条最要小心：静态扫描说"这里有幂等键"，不等于"这个幂等键有效"。所以 L2 和 L3 必须配合——静态找缺失，动态验有效。任何一层单独用都会漏。

七、真正的解法：把它前移到写代码的时候

既然根因是结构性缺失，那最有效的时点是写代码的时候，不是测试的时候。

把上面那张四类防护检查表变成 MR 自检清单：

  • 这个入口有副作用吗？→ 有幂等键吗？
  • 涉及状态流转吗？→ 有前置状态守卫吗？
  • 接收外部回调吗？→ 有去重吗？
  • 有本地队列吗？→ 重放时检查已成功了吗？

四个问题，比全量 code review 便宜得多，而且能部分自动化（模式匹配找有没有幂等键参数、有没有去重查询、有没有状态判断）。

挂到 CI 上，合并前就报告"这个新增的副作用入口没有幂等防护"——这才是"避免"，而不是"测出来"。

一句话

重复支付不是"点得快"造成的，是"重试时没人拦"造成的。 你测点得快，永远测不到没人拦。
